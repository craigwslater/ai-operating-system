# Commitment-Verification Audit

**MANDATORY before declaring session complete.**

This audit prevents the failure mode where Claude tells Craig "X is done" without X actually being persisted. Past sessions have shipped on Claude's claimed-completion that turned out to be incomplete; this rule eliminates that.

**Trigger:** Any time Claude is about to say "session is done," "everything is shipped," "files are saved," "[task] is committed/persisted/written," or any equivalent claim of completion.

**This audit is deliberately NOT gated on `/end-session`, and must not become one.** Its trigger is *any* completion claim, including mid-task ones — `CLAUDE.md` → Verify-before-claim-complete binds it to per-step verification as much as to the seal. Gating it would delete a check that is supposed to fire while work is still in flight.

**But running it is not authorization to seal.** `policies/session-end.md` executes only when Craig types `/end-session` (see the gate at the top of that file). Auditing your commitments and ending Craig's session are different acts, and finishing the first never licenses the second — the natural next thought after a clean audit is "so we're done," which is exactly the step that is not Claude's to take.

**Runs after, and independently of, the closing verifier.** A session that wrote files spawns an independent verifier subagent first (`policies/closing-verifier.md` — `policies/session-end.md` step 5.8; standing-authorized, never asked for). A clean verifier does **not** discharge this audit and this audit does not replace the verifier: one is an outside reader checking the writes against the claims, the other is Claude checking its own enumerated commitments. They are kept separate because they fail in different ways — and a self-check that has already been "confirmed" by a subagent it briefed is the failure mode both exist to prevent.

**Required steps before making any such claim:**

1. **Enumerate every commitment made during the session.** Start by reading `~/aios/outputs/commitment-logs/{session-id}.jsonl` — populated by `hooks/post-tool-use-verify-write.sh`, this is ground truth for **tool-mediated writes only** (one line per Write/Edit: `file_path` + `tool_name` + `timestamp` + `session_id` + `verified`). Since 2026-08-24 a **second** writer, `hooks/post-tool-use-observe-bash-writes.sh`, records Bash-mediated changes into the same file with `source: "mtime-observed"`. The two classes are NOT interchangeable: a tool-mediated record carries a real `verified` verdict, an observation carries `verified: null` and says only that a path's mtime moved inside a known command window. Enumerate from both; trust only the first as verification. An observation record adds `source`, `outcome`, and a truncated `command`. **Enumerate the tool-mediated records first**; the observation records and the conversation walk both pick up only what those missed. Then walk back through the conversation to add commitments NOT captured by the log: declarative-only commitments ("I'll surface this to Craig"), cross-file propagation promises that may not have landed yet, deliverable-presence checks beyond the raw write, and process-rule additions implied by completed task entries. Include both commitments made in chat and commitments implied by completed task entries.

1.1. **Cross-check the log against the filesystem — `not-logged ≠ not-written`.** The hook is a `PostToolUse` matcher on **Write/Edit only**, so every write made through `Bash` — a `python3` heredoc, `sed -i`, a generator, `regenerate-index.sh` — fires no event and never appears. The Write/Edit logger does not report that gap or degrade loudly; it returns a clean, plausible, `verified:true` list that simply omits those files, so an audit that trusts it as complete verifies a subset and still reports "all commitments verified" — the Eval-14 failure re-entering through the instrument. The Bash observer now records most of those files, which is why the cross-check's output gained an `observed:` count and per-file attribution marks. **Those marks are worded by provenance:** run WITH a session id they read `[this session — Bash]`; run WITHOUT one — which is how every invocation in these policies is written — the log is chosen by mtime, may belong to another session, and the marks read `[anchoring log — Bash]` under an explicit warning. Pass the session id when you want the strong form. What the observer does NOT do is make the log complete, so the reasoning below stands unchanged. This is the sibling of `docs/detector-design-rules.md` rule 2 ("couldn't-parse ≠ clean"), and the risk scales with how scripted the session was: a bulk `python3`/`sed` session can log **zero** writes.

   Run the coverage cross-check and enumerate its `UNLOGGED` list alongside the log:

   ```bash
   ROOT=~/aios; [ -d "$ROOT" ] || ROOT=~/mnt/aios
   python3 "$ROOT/scripts/check-write-coverage.py"
   ```

   Measured at the `workspace-audit` S11 seal (2026-07-29): **13 logged operations covering 2 distinct files**, against **≥16** distinct files actually written — 9 further content files went through Bash. (Operations and files are different units; any single "13 of N" ratio is imprecise, which is why both are stated.) **Honest limits of the cross-check** — it reports *paths*, never *causes*: it cannot attribute a write to a command, cannot distinguish a content edit from a touch, and reports `DEGRADED` rather than a verdict when it has no anchor. A `DEGRADED` line is not a clean line.

2. **For each commitment, perform a read-back verification:**
   - **File edits / new files:** Read the file (or grep for the specific change) and confirm the change is present.
   - **Cross-project propagation:** Check that updates that should be in multiple files (e.g., v4-candidate entries that go in both job-search/CONTEXT.md AND projects/job-materials-v4/CLAUDE.md) are in all required locations.
   - **Deliverables:** Verify file presence in the archive (e.g., `projects/[name]/outputs/`) and in any delivery target that actually exists (a Desktop copy, a Cowork `present_files` card), with matching byte sizes / md5 hashes. `policies/file-delivery.md` bans saving output files to Desktop, so a Desktop copy is never *required* — verify one only where it was genuinely produced.
   - **Skill-canonical updates:** Verify the change is in the source file (not just in the delivered .docx) — see Skill Update Persistence section.
   - **Self-referential figures are forbidden outright — re-measuring cannot fix them.** A precise figure describing the file it is *written into* is invalidated by the act of writing it: a `log.md` entry that states its own token count moves that count as it is typed. This is **unsatisfiable as specified**, not a discipline failure, and no amount of re-measurement closes it. So: in a `log.md` entry, never record a precise token/size figure **for that same `log.md`** — record the budget state qualitatively and name the command that produces the number (e.g. *"under the M4 threshold; run `python3 scripts/check-append-only-compaction.py` for the current value"*). The identical rule applies to a `CONTEXT.md` line quoting `CONTEXT.md`'s own budget. **`log.md` extends one step further: no precise figure for `log.md`'s size belongs anywhere in the seal's artifacts, not merely inside `log.md` itself** — `session-end.md` step 6.5 item 2 can re-touch `log.md` (an addendum line or a `touch`) *after* every figure has been measured, so even a cross-file quote of it in `CONTEXT.md` is invalidated by the seal's own repair. Precise figures remain **required** for every other file the entry does not live in. Lived **4× inside one seal** on 2026-07-29 (`concurrent-session-execution` S12), with the re-measure rule below already in force and followed: the `CONTEXT.md` net figure was rewritten three times (2,225 → 2,298 → 2,312) as later edits landed, and the `log.md` token figure was abandoned mid-seal because the entry's own prose kept moving it.
   - **Quoted measurements — re-measure, never carry the mid-session number.** Any token count, file size, or budget figure written into `CONTEXT.md`, a `log.md` entry, or a ROADMAP entry is re-measured *now*, at the seal, and corrected if it moved. **"Now" means after this audit and the closing verifier have finished** — a fix either of them surfaces re-touches a measured file and invalidates any figure taken earlier, which is how the 4× recurrence above happened. The re-measure is therefore ordered last, at `policies/session-end.md` step 6.5, not at the moment the figure is first written. A figure is measured where the work is (mid-session, to make a decision) and written where the seal is, and any later edit in the same session silently invalidates it. Lived 3× on 2026-07-28 in one session: `CLAUDE.md` measured 3,496 then landed at 3,502 — 2 over its budget; `policies/memory-architecture.md` recorded as 9,677, finished at 9,812; the sealing `CONTEXT.md` recorded as 2,398, finished at 2,394. All three were caught by closing verifiers, none by a protocol step. This is the cheap half of that finding (`skills/end-session/ROADMAP.md`); an as-of-dating convention and a re-measuring detector remain open there.

3. **For any commitment that fails verification:** fix it BEFORE making the completion claim. Do not say "done" if any commitment is unverified.

4. **Report the audit explicitly to Craig** before declaring completion. Even a one-line "Audit: 7 commitments, all verified" is enough — the discipline is the audit, not the report length. If any commitment was missed and required fixing, name it.

**Pattern to avoid:** "Done — eval-X written, SKILL.md updated, CONTEXT.md updated" without having verified each. This is the exact failure mode that produced the issue Craig flagged in Session 25 ([REDACTED COMPANY]) — Claude said v4 candidates were captured but they were only in CONTEXT.md, not in the canonical v4 project file where the eval-13 convention had established they belong.

**Why this discipline is mandatory:** Every claim of completion that turns out to be partial requires Craig to manually re-derive what was missed. The cost compounds across sessions because the missed work creates cross-session canonical drift (Eval 14 Category A class). The audit is cheap (3-5 minutes) and the failure mode it prevents is expensive (full review-cycle re-runs).
