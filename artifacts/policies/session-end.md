## The session-level closing tail — one copy, no subsets

Steps 1 through 6.5 below **are** the session-level closing tail. Any command that performs a project-level seal — `/end-session`, `/close-project`, or anything added later — **inherits the entire set**. There is no partial inheritance by default.

A consumer may drop a step only by **naming that step explicitly, with its reason**, in its own file. Everything it does not name, it runs.

**Do not restate the inherited steps anywhere else.** A consumer that lists the steps it *does* run has made a second copy of this contract, and a second copy drifts the moment a step is added here. That is exactly how `RA-LIFE-001` happened: `/close-project` named two of the eighteen steps below as though they were the complete remainder, silently dropping the closing verifier (5.8) and the seal record (6.5) from the one workflow whose writes — in-place compaction, registry row move, index regen — are irreversible. **Name your exclusions; inherit the rest by reference.** Pinned by `hooks/tests/test-close-project-tail.sh`.

**Write-order invariant — a three-way ordering, both drift-guard detectors (R-02 item 9 / fable-os-review B2 rider, 2026-07-18; extended to Detector A 2026-07-29; *scoped* at CSE P2.5c-4, 2026-08-26).** The **seal tail's** last four filesystem touches must occur in this order, and nothing within the tail may re-touch an earlier one afterward — ⚠️ **with one exemption, stated here rather than argued elsewhere: the `log.md` / `log-archive.md` pair is ONE anchor element and may be re-touched at any point.** §2.6's compaction and the re-entry paths' terminal re-touch both rely on that exemption; without it in the rule itself, the rule remains self-contradicted (see *Scope* below):

> **`CONTEXT.md` → `log.md` → `MEMORY.local.md` → `INDEX.md`**

Each arrow is a live constraint:

- **`log.md` after `CONTEXT.md` — Detector A.** The guard's *seal anchor* is `max(mtime(log.md), mtime(log-archive.md))`, and it flags every **in-scope** project file newer than that anchor. In scope = the project's top-level files plus `outputs/*` (`inputs/` and other work subdirs are excluded, as are dotfiles and hook-owned state). So any post-Step-2 `CONTEXT.md` edit makes `CONTEXT.md` newer than the anchor. The CLOSE_WINDOW exemption that forgives this does **not** apply here — it is scoped to `lifecycle = closed` projects only, so on every *active* project the mtime comparison is unmitigated. ⚠️ **CORRECTED 2026-08-26 (CSE P2.5c-4) — this sentence read "and arms a false flag at the next session start," and that is now false for a sealed project.** `[MEASURED 2026-08-26]` Since `P2.5c-2b-ii` Detector A decides on **content**, so the consequence is not a flag but a **class-A `mtime=DRIFT, content=CLEAN — DISAGREE` row** in the dual-verdict block, on every rendered report until the project's next full seal. ⚠️ **A false flag is still the consequence for a project with no `.seal.json`**, which decides on the Constraint-36 mtime fallback — so the ordering keeps its original force there, and the sentence above is retained rather than deleted for exactly that population. **Which population is a per-project test — `[ -f projects/<slug>/.seal.json ]`** (the workspace aggregate `ls -d projects/*/ | wc -l` vs `ls projects/*/.seal.json | wc -l` answers a different question). ⚠️ **Never quote a coverage figure AS CURRENT** — it moved 17/54 → 33/55 inside one day. **Scope — what this constrains, what it never did, and the re-entries with their own ordering (CSE P2.5c-4, 2026-08-26).** The ordering above governs the **seal tail**.

**Premise: `log.md` and `log-archive.md` are ONE anchor element, not two.** `hooks/session-start-drift-guard.sh` computes the seal anchor as `max(mtime(log.md), mtime(log-archive.md))`, so §2.6's compaction is **harmless to Detector A** — moving entries between the pair moves the anchor **forward**, which it can never read as drift. ⚠️ **Harmlessness alone would not have been enough:** §2.6 runs inside the tail and after Step 2.5's writes, so it *does* re-touch an earlier element. **That is why the exemption is written into the invariant itself above, by name** — the rule is now true as written, not merely harmless in practice. The guard's own header says as much, calling that compaction "the last project-dir write of a clean close." ⚠️ **The two canonical documents place compaction on opposite sides of the registry write** — §2.6 here runs *after* Step 2.5, while `skills/end-session/SKILL.md` runs it at **Step 4.5**, *before* Step 6's propagation. The anchor argument makes it harmless either way, which is exactly why the disagreement has gone unnoticed; it is recorded here rather than silently normalized.

**Two procedures genuinely re-enter after the tail has run** — the post-close addendum fast path (`policies/post-close-addendum.md`) and `policies/session-start.md` Step 4.5 Tier 5. Neither is an exemption; both share one ordering, stated once:

- **The addendum fast path and `policies/session-start.md` Step 4.5 Tier 5 are re-entries**, and both write `log.md` (the addendum) *before* `CONTEXT.md` (the status re-propagation) — the reverse of the tail's order, and deliberately so, since the addendum must exist before the status derived from it. Each therefore **ends by re-establishing the anchor**: a final `log.md` re-touch after the re-seal.

**Why this scope had to be written down.** Until 2026-08-26 the invariant read as absolute while two of this document's own procedures violated it. That is the reason underneath *"the write-order invariant regressed FOUR times after being fixed"* (`skills/end-session/ROADMAP.md`): four regressions against a rule that contradicts itself is not four lapses of discipline. A rule its own document cannot follow is one sessions route around. **Do not fix this by loosening the invariant to prose** — both detectors still key on the ordering wherever content identity has not reached (Constraint 36).

**Repair sequence when a late edit happens** (and it will — Steps 5.5/5.7, the audit, and the closing verifier all exist to surface late fixes): after any post-2.5 write to an in-scope project file, re-touch `log.md` — an addendum line if the edit was semantic, a bare `touch` if it was not — **and then** re-stamp `MEMORY.local.md` and regenerate `INDEX.md`, in that order. ⚠️ **That is the ORDERING remedy, not the CLEARING one.** Under content authority none of those three moves a hash (`SEAL_ARTIFACTS` excludes the log pair; Detector B compares the row and CONTEXT-Status hashes), so a late in-scope edit is cleared only by **re-writing `.seal.json`** — step 6.5.3. Do both. Enforced at step 6.5.

**Why this needed stating.** Only Detector B's re-stamp was ever documented; Detector A had no protocol rule at all, so a seal could trip it twice without noticing — which is exactly what happened at the `memory-hardening` interlude seal on 2026-07-28.       ```bash

      ```bash
      python3 "$ROOT/scripts/seal-record.py" write --slug <project-name>
      ```

Under concurrent sessions that is the whole difference between a signal that composes and one that does not.

      **Order matters and this is why it is step 3, not step 1.** The record hashes the project's registry row and its CONTEXT Status block, so it must be taken *after* step 2's re-stamp — a record written before the final `MEMORY.local.md` propagation would bake in a row hash that is already stale, and Stage 3 would then read a manufactured drift signal on the next start.
