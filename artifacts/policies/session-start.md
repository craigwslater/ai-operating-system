# Session Start Protocol

Every session, after resolving `~/aios` (see `docs/environment-specific-paths.md`):

1. Read `CLAUDE.md` — behavioral rules
2. Read `MEMORY.md` (shared-core identity + preferences) **and** `MEMORY.local.md` (per-machine overlay — the Active Projects registry + E-Commerce Brand). Both load at session start; if the overlay is absent (a fresh machine not yet seeded), proceed on the shared core alone.
3. Ask Craig what we're working on
4. **Relevance step — load the connected cluster, not the whole store.** If Craig's answer maps to a known project, run `bash ~/aios/scripts/query-index.sh --project <name>` and read the files it returns: the project's `CONTEXT.md` plus its typed-edge neighbors (the skills it uses, the policies governing them, the docs it points to) — the task-relevant cluster, traversed from the typed index `INDEX.md`, instead of all of memory. If the task names no project, run `bash ~/aios/scripts/query-index.sh --keyword <term>` to surface the matching cluster. If the query prints a `WEAK-RETRIEVAL`, `STALE WORKING SET`, `REJECTED DECLARATION`, `FALLBACK`, or keyword-mode `UNDER-RETRIEVAL` warning — or the script cannot run — the traversal is not trustworthy: fall back to reading `projects/[name]/CONTEXT.md` directly and scanning the `MEMORY.local.md` Active Projects registry. `INDEX.md` is loaded on demand by this step only — it is never part of the session-start eager-load (T0 + T1).
    - **Sufficiency gate — mandatory before Step 6 (RA3-02).** After loading the cluster, state **SUFFICIENT** or **WIDENED (what was added)** in the first substantive response. Retrieval coverage is a declared decision, never a silent assumption: the failure this closes is retrieval starvation converting into confabulation — the model answers from training or inference instead of abstaining, which is how PR-10 made a 2026-06-28 decision without retrieving the recorded 06-23 one. The script prints a `SUFFICIENCY CHECK:` line at the end of every cluster as the mechanical prompt; this sentence is the obligation. A `WEAK-RETRIEVAL`, `STALE WORKING SET`, or `FALLBACK` warning makes SUFFICIENT unavailable until the gap is closed — and the durable fix is a `## Working set` declaration in the project's CONTEXT.md, not a re-query. *(Same family as the `UNVERIFIED:` completion-evidence convention — an honest label on what the evidence actually supports. One idiom, two surfaces; not a second mechanism.)*
    - **Initiative branch (product-os B1).** If the mapped project is a **product initiative** — its `CONTEXT.md` has a `lifecycle-stage:` field (scaffolded from the `templates/product-initiative-*` pair) — load the **current stage's chain**, not the whole history: (i) the CONTEXT.md **Lifecycle state** block (current stage, stage table, current-stage chain block); (ii) the resolved **Chain input** artifact named in the chain block; (iii) the current stage's skill(s) per the chain block (each carries its own "Lifecycle chaining (product-os)" declaration); (iv) the declared `product-context:` router (its SKILL.md only — deeper files on demand). Prior stages' artifacts load only if the session's task requires them. `lifecycle-stage: closed` → treat as a normal project. Skip semantics are pre-resolved in the chain block at stage-transition time — read the resolved path; never recompute the skip.
4.5. **Drift reconciliation — runs only when the `SessionStart` drift guard emitted a signal.** `hooks/session-start-drift-guard.sh` injects an `additionalContext` warning at session start iff a project's in-scope files no longer match what its seal hashed (Detector A — **content**, CSE-M5, since **P2.5c-2b-ii**, 2026-08-25; it read *"files were modified after its last seal"* until then) or its registry row / CONTEXT Status block no longer matches what its seal hashed (Detector B — **content**, CSE-M6 two-hash, since P2.5c-2a). **BOTH detectors now decide on content**; an unevaluated project — one with no `.seal.json`, 37 of 54 at the flip — falls back to the old mtime comparison per Constraint 36, labelled as such in the report. On the clean path it emits nothing and this whole step is a no-op (zero model-token cost). When a signal *is* present, turn report-only detection into **append-only reconciliation** via the tiered flow below. Reconciliation is **non-blocking and scope-bounded**: the project named for *this* session is reconciled **before** substantive work (never build on a stale handoff); drift in *other* projects is surfaced and offered, then **deferred by default** if reconciling it would overrun this session's scope — it stays flagged next session (cheap by design; Claude owns the Scope-Sizing guardrail, it is not Craig's job to self-limit).

    - **Triage by signal shape (free, no reads).** The hook emits several report shapes — **do not read this list as exhaustive or as a count**; it names the ones triage branches on, and the guard has gained blocks since each time a count was written here (it was "three" until 2026-08-25 and was already short by two when corrected to "four"). Authoritative: the `REPORT=` sites in `hooks/session-start-drift-guard.sh`. The ones that matter for triage: (a) detailed individual entries (post-seal file edits, optionally carrying a registry-row finding — since P2.5c-2a worded *"Registry row is stale by CONTENT"* with the M6 clause(s) named, or *"Registry row MAY be stale"* on the Constraint-36 fallback; the pre-flip literal was "registry row also stale"); (b) a volume-cap overflow line (projects named only, beyond `DETAIL_CAP`); (c) batch-maintenance cluster lines (≥`BATCH_MIN` same-day single-`CONTEXT.md` projects, already collapsed to one named line); **(d) an `Inactive acks (suppressing NOTHING right now)` block** (CSE P2.5c-2b-i) listing content-bound acks whose recorded hash no longer matches anything firing — a **prune prompt, never a defect report**: an ack going inactive is the normal, healthy end of its life, and it is listed only because a content ack has no expiry and nothing else lists it. ⚠️ It is not inert — if that artifact ever reverts to the acknowledged content against a *newer* seal, the clause fires and the ack suppresses it under a baseline it was not taken against. That edge is **open by design** (expire-on-re-seal was rejected: it would couple the ack surface to the seal record's generation counter, and an ack is a *decision* while a seal is a *measurement*). A **cluster** defaults to "expected cross-cutting maintenance pass" — do **not** read transcripts for its members; confirm-expected with Craig and move on. **Permanent suppression (B7, built) — ⚠️ THE SCOPE DEPENDS ON WHETHER THE PROJECT HAS A `.seal.json`, and using the wrong one exits rc=3.** When Craig confirms a drift signal expected: for a **sealed** project (content decides) paste the `--scope file-set --sha256 <digest>` command **the report itself prints** — `ack.py` refuses to default the digest from disk, which is why the guard offers it pre-filled. Only for a project with **no seal record** (the Constraint-36 mtime fallback) is the watermark form still accepted — `python3 ~/aios/scripts/ack.py add --mechanism drift-guard --scope mtime --key <project> --reason "<one line: what the edits were>"` (default watermark = now; covers every edit up to this moment, and NEWER edits re-flag normally). **`--scope` is required and names the detector the ack binds (Constraint 18, CSE P2.5a):** `mtime` is Detector A's post-seal file scan. **Since CSE P2.5c-1 two more scopes are honored** — `registry-row` and `context-status`, the M6 two-hash clauses — and **since CSE P2.5c-2b-i a fourth, `file-set`** (see the paragraph below). All three bind to **content, not a clock**: each needs `--sha256 <digest>`, which the guard prints on the clause line for pasting, and `ack.py` **refuses to default it from disk** (an ack certifying whatever happened to be there when the command ran is not a decision Craig made). The bound is self-limiting — the next edit to the row or the Status block changes the hash and the clause re-flags by itself, with no expiry to tune. That bound is what made these acks safe to take **before** the authority flip — and the flip has now landed for Detector B (CSE P2.5c-2a, 2026-08-24), so a `registry-row` / `context-status` ack now removes a **reported entry**, not merely a dual-verdict qualifier. It still cannot widen: it only ever covers one exact state, and the next edit re-flags by itself. ⚠️ **`file-set` is Detector A's CONTENT scan, and since CSE P2.5c-2b-ii (2026-08-25) it REMOVES A REPORTED ENTRY** — it no longer merely records a reviewed drift set. Detector A is now **content-authoritative**, so both detectors are, and the authority split is closed. *(This sentence read "it is the one scope that clears nothing yet" until that unit; the flip is what changed it.)* ⚠️ **`--scope mtime` is RETIRED at the writer**: `ack.py add` refuses it for a project that HAS a `.seal.json` (content decides there) and still accepts it for one that does not, because a project with no seal record is decided by the **Constraint-36 mtime fallback** and an `mtime` ack still binds that. Existing `mtime` acks are never rewritten; where one has stopped binding, the report names it on a **retired-scope** line. Its bound is a **set-digest** over the whole drifted file set — all-or-nothing, so one file added, removed or changed re-flags everything. It exists now, one unit ahead of Detector A's flip (**P2.5c-2b-ii**), because contract Part 8 requires that *the ack obligation travels with authority, never after it* — the same reason P2.5c-1 preceded P2.5c-2a. ⚠️ **`mtime` and `file-set` bind the SAME detector by DIFFERENT comparisons and never quiet each other**; suppressions of the two are reported in separate blocks for exactly that reason. ⚠️ **`attribution` is still refused, and not as a queued fix** — a hash bound is a structural no-op against it (the clause fires on content the sealer already hashed), and on the different-projects MVP that clause is reporting-only indefinitely, so no scheduled unit makes it ackable. ⚠️ **A clause ack is not a project ack:** it says one clause was acknowledged, never that the project is clean — Detector A and the attribution clause are untouched by it, and so is Detector B's *other* clause. *(Until 2026-08-24 this sentence also named "Detector B's live mtime form"; that form is **gone** — P2.5c-2a replaced it with the M6 two-hash comparison these two scopes bind, which is what closed Observation F0. An **unevaluated** project — no `.seal.json` — still falls back to the mtime comparison under Constraint 36, and the report labels it when it does.)* The guard reads the surface (`scripts/acknowledgments.json`) at every start and selects on the scope column; suppressed projects stay visible on its honesty line whenever a report is emitted — **with the covered files itemized for the first `ACK_DETAIL_CAP` (=3) projects only** — beyond that the report states how many were not expanded, so read it as "the first three are itemized", never "every ack's files are listed". Separately, and for a different reason, the watermark keys on mtime-visible edits only and says nothing about a content-drifting file whose mtime sits below the seal anchor. Ack only what Craig actually confirmed — an ack is a recorded decision, not a convenience. **Overflow** names are reconciled only on request, else deferred. **Individual entries** are reconciled, tiered below.
    - **Tier 1 — the *what* (free/cheap).** The hook already names the changed files + the "sealed `<date>`" label: that is the baseline *what*. For the precise write sequence, read the originating session's commitment log — `grep` the project path across `outputs/commitment-logs/*.jsonl`, keep writes newer than the seal. **Cross-namespace caveat** (`policies/memory-architecture.md` §7 / drift-guard CLAUDE.md §7): the commitment-log id ≠ `list_sessions` id, so match by **project path + time-window + content**, never a keyed join. If the originating session has **no** commitment log (a surface or session where the PostToolUse logger wasn't active), fall back to the hook's file list + direct file reads/mtimes (the *what* is still fully recoverable). *(As of 2026-06-03 the `frontier-hooks` logger is live on both surfaces — Cowork included — so this is a robustness fallback, not the common case.)*
    - **Tier 2 gate — does the *why* need a transcript?** *Trivial* drift (a single in-scope `CONTEXT.md` touch with no semantic change, a typo, a formatting edit) is reconciled from the Tier-1 *what* alone — no transcript read. *Substantive* drift (multi-file; any `outputs/` deliverable edit; a project-`CLAUDE.md` plan change; or any case where the *why* isn't evident from the *what*) escalates to Tier 3.
    - **Tier 3 — the *why* (bounded + subagent-isolated; substantive drift only).** Find the originating session via `mcp__session_info__list_sessions` (most-recent-first; match by time-window to the drifting mtimes). Spawn a subagent whose **sole** job is: call `mcp__session_info__read_transcript(session_id, limit=N)` on the **tail** (the follow-up that caused the drift is at the tail; `limit` returns the most-recent messages), and return **only** (i) a 3–5-line "why" distillation and (ii) the drafted addendum text — **never** the raw transcript (Non-Negotiable #3, the context-bloat counter). Pass the subagent the project name, the Tier-1 file list + timestamps, the addendum template, and that explicit return contract.
      - **Past the harness's 30-day window, read the archive instead** (`memory-hardening` MH-1 / RA3-08, 2026-07-27). `mcp__session_info__read_transcript` only reaches sessions the harness still holds — Claude Code deletes transcripts per `cleanupPeriodDays` (default 30). For anything older, the durable copy is `outputs/harness-archive/projects/<slug>/<session-id>.jsonl`, written by `hooks/session-end-harness-archive.sh`; the subagent reads it **as a file**, since the MCP contract applies only to live harness sessions. Same caveat either way: **read, never parse programmatically** — the JSONL format is internal to Claude Code and changes between versions. The return contract is unchanged (distillation + addendum only, never the raw transcript).
    - **Tier 4 — write the post-close addendum (append-only / move-not-delete).** Append a `**Post-close addendum — YYYY-MM-DD (short description; reconstructed at Session N start):**` block to the **prior** session's `log.md` entry (the one whose seal the edits post-dated). Never rewrite or delete prior narrative (Non-Negotiable #2). Mirror the canonical format at `projects/activated-insights-onboarding/log-archive.md` (the Session-0 "avenue expansion" addendum; archived there 2026-06-03): what changed after the seal (origin session id + commitment-log id where known), what was asked/decided + rationale, the files touched with timestamps, and a closing line naming **why** it is an addendum (post-dated the log entry — the post-close-edit gap) and **how** it was reconstructed (commitment log for the *what*; transcript tail for the *why*, if Tier 3 ran).
    - **Tier 5 — re-propagate status, RE-SEAL, confirm clean.** If the addendum changed status/next-steps, update the project `CONTEXT.md`, re-propagate its `MEMORY.local.md` Active-Projects row (M1, ≤200 chars), and regenerate `INDEX.md` (`scripts/regenerate-index.sh`). ⚠️ **The re-propagation no longer clears Detector B by itself** — since CSE P2.5c-2a (2026-08-24) Detector B compares the row's **content** against the seal, so what clears it is the **re-seal** in the next sentence, which re-hashes the row. Correcting the row and stopping there leaves the flag up. Then **Re-write the seal record.** `ROOT=~/aios; [ -d "$ROOT" ] || ROOT=~/mnt/aios; python3 "$ROOT/scripts/seal-record.py" write --slug <project-name>` (⚠️ the bare `~/aios/…` form exits 127 in Cowork) — **after** any `MEMORY.local.md` re-stamp above, for the reason `session-end.md` 6.5.3 gives about its own ordering (*"Order matters and this is why it is step 3, not step 1"*): the record hashes the final registry row. ⚠️ **Without this step the reconciliation silences the detector on the drift it is reconciling.** The addendum's own `log.md` write moves Detector A's anchor above every drifting file, so mtime reads clean while `.seal.json` still holds the pre-drift hashes — the project reads reconciled and is not. ⚠️ **THE FAILURE MODE INVERTED AT CSE P2.5c-2b-ii (2026-08-25), and the step is still REQUIRED.** Detector A now compares CONTENT, so skipping the re-seal no longer makes the project read *clean* — it leaves the entry **firing** against stale hashes. Noise instead of silence, which is the strictly safer direction, but the reconciliation is still unfinished until the record is re-written. ⚠️ **For a project with no `.seal.json` the sentence above still holds verbatim** — it decides on the Constraint-36 mtime fallback, where the addendum's `log.md` write does still silence the detector. 6. **Confirm scope before substantive work — and size it to one session.** For any multi-step or multi-hour project session, surface the planned scope back to Craig and confirm before executing (scope confirmation is high blast radius → always an ASK, per CLAUDE.md "Decide vs Ask"). Per CLAUDE.md "Scope Sizing," never offer a scope option that Claude judges would exceed one session's context budget or force mid-session compaction: size each offered option to be doable in a single non-compacting session, and decompose larger work into discrete single-session units offered individually. Claude owns this guardrail — it is not Craig's job to self-limit.

   **A plan is not an authorization — and it never contains the seal (added 2026-08-20).** When the session runs through plan mode, `ExitPlanMode` approval covers **the unit of work as scoped** and nothing else. It does not authorize any step whose authorization is defined elsewhere, and in particular it never authorizes the **seal**: `/end-session` carries `disable-model-invocation: true`, so only Craig's typed command runs it (`CLAUDE.md` → Ongoing Structure Discipline #9). Therefore a plan file **must not contain seal or session-end steps** — no `log.md` session entry, no `.seal.json`, no registry status propagation, no Commitment-Verification Audit. A plan ends at the unit's completion and hands back.

   ⚠️ **A seal is defined by its artifacts, not by intent.** If Claude is about to write a `log.md` session entry, a `.seal.json`, or a `MEMORY.local.md` status propagation without Craig's typed command, it is sealing — whatever it is calling the work. Stop and hand back.
